# Rendering and shipping Gaussian splats in a three.js web deck (researched 2026-11-16)

The web 3DGS rendering space consolidated hard in 2025–2026 around **Spark** ([@sparkjsdev/spark](https://registry.npmjs.org/@sparkjsdev/spark/latest)), World Labs' MIT-licensed THREE.js renderer, which is now what the older three.js viewers point people at — mkkellogg's own README says it is "no longer in active development" and recommends Spark ([GitHub](https://github.com/mkkellogg/GaussianSplats3D)). Spark answers our exact integration question: `SplatMesh` is a `THREE.Object3D` drawn inside your normal `renderer.render(scene, camera)` call, and Spark does its async work from inside that same call ([docs/overview](https://sparkjs.dev/docs/overview/), [on-demand rendering](https://sparkjs.dev/docs/on-demand-rendering/)), including when the active target is a texture rather than the canvas ([PR #360](https://github.com/sparkjsdev/spark/pull/360)). three.js itself grew first-class splat support in r186 (2026-09-24) — `GaussianSplat`, `GaussianSplatPLYLoader`, `SPLATLoader`, `KSPLATLoader`, glTF `KHR_gaussian_splatting` ([releases API](https://api.github.com/repos/mrdoob/three.js/releases), [docs](https://threejs.org/docs/pages/GaussianSplat.html)) — but that path is **WebGPURenderer-only and explicitly does not support `WebGLRenderer`**, which rules it out for our current WebGL2 stage unless we run a second renderer. Format-wise, PLY is the interchange/archive format and everything else is a compression or streaming container: SPZ (~10×, [nianticlabs/spz](https://github.com/nianticlabs/spz)), SOG (~15–20×, [PlayCanvas spec v3](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/)), compressed PLY, `.splat`, `.ksplat`, plus LOD/streaming containers (.RAD, Streamed SOG, LCC2) ([formats overview](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/)). Performance is dominated by sorting (CPU radix sorts in workers for Spark/mkkellogg/antimatter15) and fill-rate/overdraw, so both Spark and PlayCanvas recommend deliberately *low* render resolutions and pixel budgets ([Spark performance](https://sparkjs.dev/docs/performance/), [PlayCanvas performance](https://developer.playcanvas.com/user-manual/gaussian-splatting/building/performance/)) — which is exactly the regime our pixelated low-res render target already lives in.

## Options

### Spark (World Labs) — recommended

- **What it is**: An "advanced 3D Gaussian Splatting renderer for THREE.js", WebGL2, built by World Labs. **Input → output**: consumes splat files (`.ply` incl. compressed, `.spz`, `.splat`, `.ksplat`, `.sog`, streamable `.rad`) → draws them in your existing three.js scene.
- **How it works**: 3-step pipeline — build one global splat list across all objects (GPU "dyno" shader-graph pass), sort back-to-front, draw as one instanced quad batch. Sorting is a two-pass radix sort **on the CPU in a Web Worker** fed by GPU-computed distances read back to the CPU; LoD is a continuous "splat tree" cut with a fixed splat budget, streamed in 64K-splat chunks ([Spark 2.0 deep dive](https://worldlabs.ai/blog/spark-2.0)).
- **Open / license**: Open source, **MIT** ([LICENSE badge + repo](https://github.com/sparkjsdev/spark/), npm `license: MIT`). ~3.9k stars, 589 forks, repo created 2025-05-23 ([GitHub API](https://api.github.com/repos/sparkjsdev/spark/pulls/360)).
- **Runs locally?** Yes — it is a client-side library; needs WebGL2 (targets "98%+ WebGL2 support"), plus WASM workers. No server, no GPU vendor lock-in ([README](https://github.com/sparkjsdev/spark/)).
- **Status / current npm version**: npm package name **`@sparkjsdev/spark`**, latest **2.4.0, published 2026-10-20** ([registry /latest](https://registry.npmjs.org/@sparkjsdev/spark/latest)); peer dependency `three >= 0.180.0`, so it is compatible with our three `0.187.0` ([package.json](https://raw.githubusercontent.com/sparkjsdev/spark/main/package.json)). Active: issues/PRs still landing in Nov 2026 ([#498](https://github.com/sparkjsdev/spark/issues/498), [#499](https://github.com/sparkjsdev/spark/issues/499)).
- **Renders into OUR render target?** **Yes.** `SplatMesh` "derives from `THREE.Object3D`… rendered during your regular `render(scene, camera)` call" ([overview](https://sparkjs.dev/docs/overview/)); Spark "does its work from inside `renderer.render()`" ([on-demand](https://sparkjs.dev/docs/on-demand-rendering/)); PR #360 infers linear-sRGB output "from the currently bound render target… e.g. render to texture" ([PR](https://github.com/sparkjsdev/spark/pull/360)); there is also an explicit offline `target: {width, height}` + `renderTarget()` API for offscreen/secondary viewpoints ([SparkRenderer options](https://sparkjs.dev/docs/spark-renderer/)).
- **Fit for our deck**: Best option by far — add one `SparkRenderer` + one `SplatMesh` per scene inside `src/scenes/pixel-viz.js`'s `scene`, and the splats go through the existing low-res RT and dither pass for free; caveat: it is a new runtime dependency (task rules say don't add deps → needs owner approval).

### three.js native `GaussianSplat` (r186+)

- **What it is**: First-class splat mesh + loaders shipped *in* three.js (addon path `three/addons/objects/GaussianSplat.js`). **Input → output**: `BufferGeometry` from `GaussianSplatPLYLoader` / `SPLATLoader` / `KSPLATLoader` / glTF `KHR_gaussian_splatting` → a `Mesh` subclass in the scene.
- **How it works**: TSL/WebGPU implementation with GPU counting sort (`updateSort`) and a compute pass for view-dependent SH ([docs](https://threejs.org/docs/pages/GaussianSplat.html)); landed in r186 (2026-09-24) by @bhouston et al. ([release notes via API](https://api.github.com/repos/mrdoob/three.js/releases)).
- **Open / license**: MIT, same as three.js. **Runs locally**: yes, browser only.
- **Status**: three `0.187.0` on npm (2026-10-30 release of r187) ([registry](https://registry.npmjs.org/three/latest), [API](https://api.github.com/repos/mrdoob/three.js/releases)).
- **Blocks us**: "this class can only be used with `WebGPURenderer`… `WebGLRenderer` is not [supported]" ([docs](https://threejs.org/docs/pages/GaussianSplat.html)). Our deck uses `THREE.WebGLRenderer` ([src/scenes/pixel-viz.js:540](../../../src/scenes/pixel-viz.js)). `WebGPURenderer`'s `forceWebGL` fallback *is* supported per the same page — untested here for our dual-target/post-process setup.
- **Fit**: No for the current stage; revisit if/when the deck moves to `WebGPURenderer` (then it is the zero-dependency path).

### Spark "Radix" (`@sparkjsdev/radix`)

- **What it is**: npm describes it as "An advanced WebGPU 3D Gaussian Splatting renderer for THREE.js" ([registry](https://registry.npmjs.org/@sparkjsdev/radix/latest)).
- **Status**: **0.0.1, published 2026-10-29**, MIT — i.e. brand-new/experimental, effectively the WebGPU rewrite.
- **Fit**: Watch-list only; too young to put on stage, and WebGPU-targeted like the native path.

### mkkellogg GaussianSplats3D

- **What it is**: The original THREE.js 3DGS viewer/renderer. **Input → output**: `.ply` (INRIA v1/v2 + PlayCanvas-compressed), `.splat`, `.ksplat` → splat mesh in a three.js scene.
- **How it works**: Splat data packed into data textures, WASM-SIMD **CPU** sort in a worker with a transform-feedback-assisted pre-pass, octree culling ([README](https://github.com/mkkellogg/GaussianSplats3D)).
- **Open / license**: MIT, © 2023 Mark Kellogg (LICENSE in repo). npm **`@mkkellogg/gaussian-splats-3d` 0.4.7, published 2025-01-25** ([registry](https://registry.npmjs.org/@mkkellogg/gaussian-splats-3d/latest)).
- **Status**: Explicitly unmaintained — README: "no longer in active development… recommend checking out Spark". Known issues listed: CPU-only sort, artifacts under fast motion, "sub-optimal performance on mobile devices" ([README](https://github.com/mkkellogg/GaussianSplats3D)).
- **Renders into our RT?** Partially: `DropInViewer extends THREE.Group` and drives `viewer.update(renderer, camera)` from a `callbackMesh.onBeforeRender`, so it hooks the normal render path ([src/DropInViewer.js](https://github.com/mkkellogg/GaussianSplats3D/blob/master/src/DropInViewer.js)) — but its own docs describe it as driving its own viewer/scene, and "Allows a Three.js scene or object group to be rendered along with the splats" is the weaker fusion Spark was built to fix.
- **Fit**: Only as a fallback if Spark ever blocks us; ~22 months stale.

### PlayCanvas engine + SuperSplat (different engine)

- **What it is**: PlayCanvas is "Open-source WebGL/WebGPU 3D engine" (npm **`playcanvas` 2.24.1**, MIT, 2026-11-12) with first-class `gsplat` rendering; SuperSplat is the browser editor/publishing platform on top of it ([formats](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/), [editor docs](https://developer.playcanvas.com/user-manual/supersplat/editor/)).
- **Engine features worth stealing**: a **global splat budget** (`app.scene.gsplat.splatBudget`, default 1,000,000) driving Streamed-SOG LOD, `lodBaseDistance`/`lodMultiplier`, `lodRangeMin/Max`, plus explicit advice to disable anti-aliasing and device-pixel-ratio because "3DGS is particularly expensive in terms of fill rate" ([performance](https://developer.playcanvas.com/user-manual/gaussian-splatting/building/performance/)).
- **Renders into our three.js RT?** **No** — it is a separate engine/renderer; you'd embed it as its own canvas/iframe (`@playcanvas/web-components` 0.30.0, MIT, [registry](https://registry.npmjs.org/@playcanvas/web-components/latest)), which loses our shared dither pass.
- **Fit**: Not a runtime option for the deck, but the *best* tooling around it (see SuperSplat + splat-transform below).

### Babylon.js (different engine)

- **What it is**: `GaussianSplattingMesh` + loader plugin, first-class since Babylon 8.0 (2025-03) ([Babylon 8.0 announcement](https://blogs.windows.com/windowsdeveloper/2025-03-31/part-2-babylon-js-8-0-audio-gaussian-splat-and-physics-updates/)). npm **`@babylonjs/core` 9.37.0**, **Apache-2.0** ([registry](https://registry.npmjs.org/@babylonjs/core/latest)).
- **Formats**: PLY (incl. compressed + half-float), `.splat`, `.spz` (incl. **v4**, SH to order 4), SOG/SOGS, glTF `KHR_gaussian_splatting`, Streamed SOG (`lod-meta.json`) ([docs](https://doc.babylonjs.com/features/featuresDeepDive/mesh/gaussianSplatting)).
- **Sorting evidence (useful cross-check)**: worker sort with O(n) **counting sort** by default, `viewUpdateThreshold` to skip sorts, `minPixelSize` culling, opt-in **WebGPU compute GPU sort** ("on low-end GPUs the asynchronous CPU worker can be faster"), and an experimental WebGPU "point splatting" mode that skips sorting entirely ([docs](https://doc.babylonjs.com/features/featuresDeepDive/mesh/gaussianSplatting)).
- **Renders into our three.js RT?** **No** — Babylon engine, its own scene/renderer.
- **Fit**: Reference material (their debug overdraw/projected-size plugins describe exactly the metrics we care about at low resolution), not a component.

### Luma: `@lumaai/luma-web` and luma.gl

- **`@lumaai/luma-web`**: "LumaSplatsWebGL… LumaSplatsThree, which is a Three.js implementation" ([repo](https://github.com/lumalabs/luma-web-examples)) — designed to be embedded in a 3D framework, i.e. historically one of the few three.js-native options. Status: **0.2.2, last published 2024-03-06**, MIT ([registry](https://registry.npmjs.org/@lumaai/luma-web/latest)) → effectively frozen, and tied to Luma-hosted "Interactive Scenes" (closed capture/service).
- **luma.gl**: `@luma.gl/engine/splats` (npm `@luma.gl/engine` 9.4.2, MIT) offers "experimental GPU-native Gaussian splat rendering… GPU picking… bounded residency… foveated LOD", but "graph renderers, GPU ordering, and storage-backed features **require WebGPU**"; use the prepared `SplatRenderer` path "when WebGL 2 compatibility… is required" ([docs](https://luma.gl/docs/api-reference/splats)).
- **Fit**: No — wrong framework (deck is React + three; luma.gl would mean replacing the renderer) and WebGPU-gated for the interesting parts.

### gsplat.js (Hugging Face)

- **What it is**: "open-source 3D Gaussian Splatting library, providing functionality similar to three.js **but for Gaussian Splatting**" — its own `Scene/Camera/WebGLRenderer`, not a three.js addon ([README](https://github.com/huggingface/gsplat.js/)). npm `gsplat`.
- **Open / license**: MIT; README flags that the underlying INRIA research project is **non-commercial** and that "users should consider the source of the splat data separately".
- **Renders into our three.js RT?** No (separate renderer).
- **Fit**: No. Its `.splat` conversion examples are handy but `splat-transform` is better maintained.

### antimatter15/splat (viewer + the `.splat` format)

- **What it is**: The original WebGL 1.0 viewer that defined the 32-byte `.splat` layout; now recommends Spark for "more advanced" work ([README](https://raw.githubusercontent.com/antimatter15/splat/master/README.md)).
- **Why it still matters**: its README is the clearest primary-source account of the sorting problem — naive CPU painter's sort of ~1M splats measured at "~150 ms"; their shipped approach sorts on the CPU in a worker at roughly **4 fps** vs 60 fps render, accepting temporary z-order errors; no SH (view-dependent colour) in the format; WebGPU bitonic sort dismissed as ~200 iterations for 1M values.
- **Fit**: No as a renderer (2023-era, no SH, own GL context). Good citable source for the "sorting is the cost" slide.

### SuperSplat Editor (cleaning/cropping a capture) + `splat-transform` (compressing it)

- **SuperSplat Editor**: "open-source, browser-based editor… clean up raw splat captures, trim floaters, crop scenes, retouch colors, build camera animations, and publish" — **MIT**, GitHub [playcanvas/supersplat](https://github.com/playcanvas/supersplat), runs at [superspl.at/editor](https://superspl.at/editor); **requires a WebGPU-capable browser** (Chrome/Edge, Safari 26+, or Firefox with WebGPU enabled), nothing uploaded until you publish ([editor docs](https://developer.playcanvas.com/user-manual/supersplat/editor/)). Imports/exports `.ply`, `.compressed.ply`, `.sog`, `.splat`, `.ksplat` (import only), `.spz` (writes SPZ v4 by default, v3 for old readers), `.lcc/.lcc2`, and a self-contained `.html` viewer app ([import/export docs](https://developer.playcanvas.com/user-manual/supersplat/editor/import-export/)).
- **`@playcanvas/splat-transform`** (npm **3.11.2**, MIT, [registry](https://registry.npmjs.org/@playcanvas/splat-transform/latest)): CLI to crop/clean/shrink without a GUI — `--filter-box`, `--filter-sphere`, `--filter-nan`, `--filter-floaters` ("remove Gaussians not contributing to any solid voxel"), `--filter-cluster`, `--decimate`/`--decimate-adaptive`, `--filter-harmonics`, `--stats` (prints fill/overdraw ratio), `--webp-effort` ([README](https://raw.githubusercontent.com/playcanvas/splat-transform/main/README.md)). Reads PLY/Compressed PLY/SOG/Streamed SOG/SPZ/SPLAT/KSPLAT/LCC(2); writes PLY/Compressed PLY/SOG/Streamed SOG/SPZ/GLB/CSV/HTML viewer/LOD/voxel.
- **Postshot** (Jawset): commercial desktop capture+training app; "**runs all processing and machine learning steps on devices only you have access to**", CLI + GUI, unlimited image count/model size, ACES, region-of-interest training ([jawset.com](https://www.jawset.com/)) — a genuinely local (Windows/Linux/Mac; per-OS availability and price **unverified**) way to make a splat from photos.
- **Fit**: This is the pipeline for producing a slide asset: capture/obtain → SuperSplat (or `splat-transform --filter-box --filter-floaters`) to crop the junk → `splat-transform` to `.sog`/`.spz` → ship ~5 MB next to the deck.

### Bake it offline instead of rendering live (fallback)

- SuperSplat exports a **self-contained `.html` viewer** and publishes streamed SOG scenes, and Spark can render to an offscreen target and `readTarget()` back to RGBA bytes ([SparkRenderer docs](https://sparkjs.dev/docs/spark-renderer/)) — both make it practical to pre-render an orbit/turntable of a splat scene and ship it as a video/PNG sequence, dropping `<video>`/texture into a scene with zero runtime splat machinery, zero sorting and zero extra WebGL contexts.
- **Fit**: The lowest-risk option for the talk itself (live demo failure modes disappear); costs interactivity, and needs the offline step done before the deck is frozen.

## Formats, sizes, streaming and sorting (what the sources actually say)

- **PLY**: row-major, float32, uncompressed. "10M splats with SH0..3 may consume up to **2.3 GB**" ([Spark 2.0](https://worldlabs.ai/blog/spark-2.0)); independently, ~220 MB per 1M splats and a "compressed PLY ≈ ¼ size" rule of thumb from a studio's measured tables ([note.com/steam_studio](https://note.com/steam_studio/n/ne9736d94f162)).
- **`.splat`**: 32 bytes per splat (8×float row, positions/scales/quat/colour+alpha) — from Babylon's `updateData` buffer spec ([docs](https://doc.babylonjs.com/features/featuresDeepDive/mesh/gaussianSplatting)); no SH, so colours are view-independent ([antimatter15 README](https://raw.githubusercontent.com/antimatter15/splat/master/README.md)). ~32 MB per 1M splats.
- **SPZ**: column-major + compressed, "typically around **10× smaller** than the corresponding `.ply` with minimal visual differences"; v4 = ZSTD with a 32-byte plaintext header and per-stream parallel compression (v1–3 = single gzip stream) ([nianticlabs/spz](https://github.com/nianticlabs/spz)); Spark added SPZ v4 read support in 2.4.0 ([npm changelog](https://www.npmjs.com/package/@sparkjsdev/spark)). Downside for streaming: the whole file must arrive before any splat is complete ([Spark 2.0](https://worldlabs.ai/blog/spark-2.0)).
- **SOG (Spatially Ordered Gaussians)**: per-property quantized 8-bit **WebP** textures + `meta.json`, 16-bit log-domain positions, 24-bit exponential-map rotations, codebook scales, SH palette; "**~15–20× smaller** than an equivalent PLY", lossy by design; bundled `.sog` = a zip ([spec v3](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/)); colours are **sRGB display-referred and blended in sRGB** (§3.4.1) — relevant to our palette/dither shader.
- **Streaming / LOD**: Streamed SOG (`lod-meta.json`) = SOG chunks in a spatial tree ([formats](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/)); Spark's **.RAD** = JSON header + random-access 64K-splat chunks with a continuous LoD tree built by Tiny-LoD (in-browser, WASM) or Bhatt-LoD (CLI `build-lod`) ([Spark 2.0](https://worldlabs.ai/blog/spark-2.0)); Babylon streams PlayCanvas-style Streamed SOG on WebGL2 *and* WebGPU ([docs](https://doc.babylonjs.com/features/featuresDeepDive/mesh/gaussianSplatting)); XGRIDS LCC2 is the scanner-vendor equivalent ([formats](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/)).
- **Sorting**: Spark = GPU distance + CPU two-pass radix sort in a worker ([blog](https://worldlabs.ai/blog/spark-2.0)); mkkellogg = WASM SIMD CPU sort, with "artifacts when you move or rotate too fast" ([README](https://github.com/mkkellogg/GaussianSplats3D)); antimatter15 ≈ 150 ms per 1M-splat CPU sort, sorted at ~4 fps ([README](https://raw.githubusercontent.com/antimatter15/splat/master/README.md)); Babylon = worker counting sort, opt-in WebGPU compute sort, with an explicit warning to measure before enabling ([docs](https://doc.babylonjs.com/features/featuresDeepDive/mesh/gaussianSplatting)).
- **Device budgets**: Spark's rule of thumb — Quest 3 ≤1M, Android phone 1–2M, iPhone 1–3M, computer 1–5M (10–20M+ on some desktops), and "at around 1 million splats [per-frame transform/sort] becomes a bottleneck on some systems"; also `antialias: false` and think twice about `devicePixelRatio` ([performance docs](https://sparkjs.dev/docs/performance/)). PlayCanvas: default budget 1M, "~1M for mobile, 3+M for desktop", and disable AA + DPR because overdraw is the bottleneck ([performance](https://developer.playcanvas.com/user-manual/gaussian-splatting/building/performance/)).
- **Implication for our deck**: rendering the splats into our small RT (e.g. 1.5-slide-px cells, `samples: 4`) is the fill-rate-friendly direction both vendors recommend, but at that resolution splats become *large* multi-pixel blobs, so the dither/palette pass will posterise gradients hard — expect to tune `tones`/`dither`, `maxStdDev`, `minPixelRadius` and `lodRenderScale` per scene, and to keep hero assets at ~100–300K splats (a studio's stated web target is 100–200K for mobile 4G: [note.com](https://note.com/steam_studio/n/ne9736d94f162)).

## Gaps and unverified claims

- Whether Spark renders correctly into a **MSAA multisampled** `WebGLRenderTarget` (`samples: 4` in [pixel-viz.js:545](../../../src/scenes/pixel-viz.js)) — not documented. Related caution: Spark docs demand `antialias: false` on the renderer ([performance](https://sparkjs.dev/docs/performance/)), and an open Quest-browser bug report describes a hang from **MSAA + a per-frame shadow pass + SplatMesh** ([issue #400](https://github.com/sparkjsdev/spark/issues/400)). Must be tested on the actual deck harness.
- Spark's `SplatAccumulator` buffers only grow: an open Nov-2026 issue reports ~900 MB GPU held where ~75 MB would do after one wide view, and a 87→115 fps improvement from a user-side trim workaround ([issue #499](https://github.com/sparkjsdev/spark/issues/499)). For a deck with ≤3 live WebGL contexts and 5–15 min slides, memory growth matters — measure, and prefer small assets. No fix confirmed as merged as of 2026-11-16 (unverified).
- Spark npm "weekly downloads ≈ 450k, 19 dependents" came from a search-result snippet of the npm page, not from a page I opened — **(unverified)**.
- `@sparkjsdev/radix` details (three-r186 WebGPURenderer + WebGL2 backend, feature set) are from its npm description; the repo README was not opened — **(unverified)**.
