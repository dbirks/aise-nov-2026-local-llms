# Method D — real-world captured splats (public, licensed samples)

Photogrammetry-style 3D Gaussian Splats: each subject was **photographed from many angles and
the Gaussians were trained on those photos** — by somebody else, on somebody else's hardware.
Nothing here is generated by a model or baked from math. We only take samples whose licence is
stated per file, so a slide can name the subject and the person who captured it.

All three come from `three.js`'s own example assets, which ship a `.license.txt` beside each
splat naming the author, the superspl.at scene and the licence (copies in
`tools/splats/d/licenses/`). three.js also records the author's *display* rotation per asset in
`examples/webgpu_gaussian_splat.html` — used below, see "Pose".

Total `public/splats/d` = **4.9 MB** (caps: 8 MB per file, 25 MB per method). "Convert" is one
`splat-transform@3.11.2` run on 8 CPU cores, nothing else on the machine (peak RSS it reports:
173–300 MB). `build.sh` calls it twice per asset — once without `-t/-s` to read the bounds, once
to write the shipped file — so its own wall clock is roughly double. No GPU required; the QA
`.webp` previews are rasterised by splat-transform through Vulkan llvmpipe. Counts and extents
come from `--stats` on the shipped files. Measured 2026-11-16.

## Reproduce

```bash
tools/splats/d/fetch.sh    # three CC-BY sources -> tools/splats/d/raw/ (gitignored) + licences
tools/splats/d/build.sh    # pose + crop + strip SH + centre + scale -> public/splats/d/*.spz
tools/splats/d/preview.sh public/splats/d/lion.spz /tmp/pv "4,2,-4" "0,0,0" 640x480   # deck-frame PNG + sage preview
```

The generator is the command line itself. Per asset the shipped file comes from:

```bash
ST='pnpx @playcanvas/splat-transform@3.11.2'

# millipede — long axis onto x, legs down; -t/-s from --stats on the same command without them
$ST -w raw/millipede.splat  -r 90,0,0 -r 0,90,0 -H 0 --spz-version 3 \
    -t -0.0436,0.0592,0.0282 -s 5.310858 ../../../public/splats/d/millipede.spz

# lion — the file stores the head upside down; three.js shows it with mesh rotation Euler(PI,0,0)
$ST -w raw/lion.v3.spz      -r 180,0,0 -H 0 --spz-version 3 \
    -t -0.0255,0.1600,-0.0508 -s 5.350748 ../../../public/splats/d/lion.spz

# tomatoes — crop to the fruit + the plate patch under it, drop the soft halo splats,
# no rotation (this one is stored upright)
$ST -w raw/tomatoes.v4.spz  -B -3.4,-4.85,-1.6,2.2,-0.02,2.6 -V opacity,gt,0.12 -H 0 \
    --spz-version 3 -t 0.5995,2.3243,-0.4996 -s 0.714429 ../../../public/splats/d/tomatoes.spz
```

`-H 0` keeps only the DC colour band (the deck discards hue anyway, and view-dependent SH would
flicker through a turntable). `--spz-version 3` (gzip) rather than the v4 default, for wider
loader support. `-t/-s` centre each asset on the origin and make its largest extent exactly
4.00 units, which fits the default ortho view (size 2.2). On the tomatoes, `-V opacity,gt,0.12`
is an editorial choice: it throws away ~16 500 soft halo splats that made the pair read as a red
cloud at slide scale (un-filtered crop = 27 911 splats / 448 KB, visibly fuzzier).

## Pose — and a coordinate trap

`splat-transform` prints `--stats` and CSV columns in the asset's **file frame**, i.e. the frame
the deck renders (+y up, three.js/Spark convention; checked against Niantic's `spz` Python
bindings reading `lion.v3.spz` as `CoordinateSystem.RUB`), but it *applies* `-r/-t/-s/-B` in its
own world frame, which is that file frame rotated 180° about z: `-t 1,0,1` moved the lion by
`(-1,0,+1)` in file coordinates, and a `-B` box has to be mirrored the same way. Its `.webp`
renders come out upside down relative to the deck too. `bounds.py` does the conversion and
`preview.sh` mirrors the camera back and rotates the image, so `preview.sh` output is what the
deck shows.

These captures carry no "up" metadata, so pose was fitted from geometry rather than guessed:
`pose.py` measures the principal axes and, for an arc-shaped subject, the circle-fit concave
direction; `fitrot.py` searches Euler triples for a target pose, measured in the file frame.
For the millipede that put the 0.753-unit body axis on x with the leg side facing −y. For the
lion, three.js applies `Euler(PI,0,0)` to the very same file, so the head really is stored
inverted and the baked 180° matches upstream intent. The tomatoes need nothing.

## Checked in the running deck

Screenshotted through `pnpm dev` at `#/gs-d-millipede`, `#/gs-d-lion`, `#/gs-d-tomatoes` on
2026-11-16: Spark decodes all three SPZ v3 files and every one is upright — lion ears up,
millipede curled leg-side down, tomatoes on their plate patch — so the pose work above agrees
with the deck. All three silhouettes survive the 6-tone sage ramp. The millipede is the darkest
subject (its brown shell lands on the two darkest tones) and the tomatoes are the softest; worth
a glance at the projector. Captures live in `tools/splats/d/work/` (gitignored).

## Caveats

* These are **somebody else's captures**; the pixels are theirs. Our pipeline only re-times,
  crops and re-encodes. Nothing here measures a model, a GPU or an inference engine.
* Cropping is a box, so the tomatoes' plate ends in straight cut edges and the millipede keeps a
  few out-of-focus floaters near its legs — visible as specks while orbiting. That is what a real
  capture looks like, not an encoder defect.
* `-H 0` removes view-dependence, so the assets are lit flat. Saturated red fruit and the dark
  plate sit at nearly the same *luminance*, so the deck's ramp flattens that contrast and the
  tomatoes read mostly as silhouette + stem detail.
* Camera framing on all three slides is a first guess (`view` in `src/slides/splat-lab/d-captures.ts`);
  the splat occupies ~4 of the 4.4-unit ortho height. The millipede's best profile is from
  ±90° of the default azimuth, so expect the orchestrator to retune `theta`.
* If a slide shows an asset upside down, the deck's SplatMesh is applying its own y flip: drop
  `-r 180,0,0` (lion) or `-r 90,0,0 -r 0,90,0` (millipede) and re-run.
