sliced to 5000 MiB by HAMi), 2026-11-17 00:52–01:08 UTC.

## How the 4.9 GiB slice fits an "≈10 GB" pipeline

[LGM's own readme](https://github.com/3DTopia/LGM/blob/fe8d12cff8c827df7bb77a3c8e8b37408cb6fe4c/readme.md#L54): "Inference takes about 10GB GPU memory (loading all imagedream, mvdream, and our LGM)" — i.e. everything resident at once. It ran inside a 5000 MiB slice because of these four choices:

1. `tools/splats/g1/mvgen.py` — rembg (u2net, onnxruntime on CPU) cut-out → `recenter(border_ratio=0.2)` → white
   background → ImageDream `ipmv` → `mv_0..3.png`. All four diffusion components ship as **F16** (verified in the
   remote safetensors headers), so their VRAM cost is their file size: UNet 1796 MiB + CLIP-ViT-H image encoder
   1203 MiB + CLIP text encoder 649 MiB + VAE 160 MiB = **3808 MiB of weights**. Measured peak torch allocation was
   **3870 MiB** with **4850 MiB** reserved, i.e. the peak is all of the weights plus ~60 MiB — it happens during the
   image encoder's single forward, before the monkey-patch drops it to CPU. That is why the patch exists: the 30
   denoising steps then run on 2605 MiB of weights with ~2.2 GiB of headroom for activations instead of ~1 GiB.
2. `tools/splats/g1/lgm2ply.py` — a **separate process**, so the diffusion's 3808 MiB of fp16 weights are gone before
   LGM loads its 791.6 MiB. The 4 views in LGM's own order `[1,2,3,0]`, bilinear to 256, ImageNet-normalised,
   concatenated with the 6-channel Plücker ray embedding (`prepare_default_rays`) → U-Net → activations →
   `[1, 65536, 14]` → `model.gs.save_ply()`. Measured peak torch allocation **1330 MiB** (1970 MiB reserved).
3. **No rendering at all.** `diff-gaussian-rasterization` is a stub (the LGM README lists it as a preview-only
   dependency), so no CUDA extension is compiled for `sm_61` and LGM's 360-frame `.mp4` is skipped — the `.ply` *is*
   the deliverable and the deck renders it.
4. `xformers` is replaced by a SDPA-backed shim: the real wheel ships SM70+ kernels and the GTX 1070 is `sm_61`. The
   shim is checked against an explicit `softmax(QKᵀ/√d)V` in fp32 and fp16 in `selftest.py` (max |Δ| 0 and 5.3e-4) and
   keeps xformers' positional `[B, H, M, K]` layout, which is what LGM's checkpoint was trained against.

What went wrong first (infra, not the model — recorded so nobody re-diagnoses it): **`splat-lab-lgm-1` died in
`setup`** with `ModuleNotFoundError: No module named 'kiui'` after torch, the wheels and the LGM checkout had all
installed fine. The `scripts` volume used ConfigMap `items:` whose `path`s contained directories
(`vendor/kiui/__init__.py`), and those nested files were not in the mount, so `run.sh`'s `cp -r /scripts/vendor` produced
a vendor tree without the `kiui` package. Run 2 mounts the whole ConfigMap, keeps every key flat
(`vendor-kiui-__init__.py`) and has `run.sh` rebuild `vendor/<pkg>/<mod>.py` from those names — the two `find` lines at
the top of the setup log are what prove it.

## Assets

Both start from a photograph of real hardware we talk about, are **generated, not scanned** (see the warning below),
and were produced by the same Job with the same settings.

```bash
# 1. in the Job (stage names, idempotent): preflight setup inputs mvgen lgm report
bash /scripts/run.sh all                     # OUT=/data/out/g1-2
# 2. get the raw .ply off the PVC
kubectl cp default/<splat-lab-files pod>:/data/out/g1-2 ./out
# 3. centre on the origin, keep y-up, largest extent 4, drop splats with alpha < 0.05
uv run tools/splats/g1/normalize.py out/gtx1070.ply out/gtx1070.norm.ply --min-alpha 0.05
# 4. pack (no decimation needed; both files are well under the 8 MB cap)
pnpx @playcanvas/splat-transform@3.11.2 out/gtx1070.norm.ply public/splats/g1/gpu.spz
pnpx @playcanvas/splat-transform@3.11.2 out/minipc.norm.ply  public/splats/g1/server.spz
pnpx @playcanvas/splat-transform@3.11.2 public/splats/g1/gpu.spz --stats text null
```

Steps 3–4 are also in [`../../tools/splats/g1/pack.sh`](../../tools/splats/g1/pack.sh). Run output for the whole Job —
`RESULTS.json`, per-stage `metrics_*.json`, `pip-freeze.txt`, the cut-outs, the 2×2 view grids and the raw `.ply`
files — is kept in [`../../tools/splats/g1/run-g1-2/`](../../tools/splats/g1/run-g1-2). The same JSON plus the full
`run-all.log` (with the `nvidia-smi` sampler rows) stays on the PVC at `/data/out/g1-2/`.

## Coordinate convention and what the visual must not imply

- LGM's world is **y-up, OpenGL-style** (`kiui.cam.orbit_camera` with `opengl=True`, camera radius 1.5, the object
  inside roughly `[-1, 1]³`). Taken as-is: `normalize.py` only translates and scales (`--rot 0,0,0 --flip ''`), so
  `+Y` stays up and the front panel of the mini PC keeps facing the same way it does in `mv_0.png`. The two
  orientation checks above are consistent with that; if the deck shows either asset lying down, re-run `pack.sh`
  with `--rot`/`--flip` — no GPU time needed.
- **These are diffusion hallucinations, not scans.** LGM never saw the back or the internals of either device: the
  four views it conditions on are themselves generated from one picture, and a generated object's colours and unseen
  geometry are only as real as the diffusion's prior. Do not present them as measured geometry of a real card, and do
  not read the proportions as product specifications: the mini PC's kept cloud is 0.40 as tall as it is wide (the
  panel in the photo looks ≈0.37, so the front face roughly agrees) and 0.74 deep — the depth, the chamfers, the
  ports and everything on the faces nobody photographed are the model's guess, not measurements.
- 65,536 is a property of the `big` config (`4 × splat_size²`, `splat_size = 128`), not a quality metric — the
  shipped count is ~20–23 k because two opacity filters removed the rest, and the deck's luminance-only post shader
  discards hue anyway.
- Timings and VRAM above are one measurement of one run on one Pascal card at batch 1, 256×256, seed 42; they are
  not a benchmark against anything and they are not the numbers an A10G/4090 would give. The 3870 MiB peak is
  PyTorch's own allocation counter; the 4943 MiB figure is what `nvidia-smi` inside the container reported (it
  includes PyTorch's cache/reservation of 4850 MiB), which is why it sits so close to the 5000 MiB HAMi slice.
- `compute` on the slides quotes the warm-cache numbers (97 s of model work / 108 s wall per object), not the 841 s of the cold run, and is quoted in MiB because the HAMi slice is specified in MiB.
